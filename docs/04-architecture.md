# Техническая архитектура

> Статус: предложение к утверждению в этапе 0. Каждое решение ниже — кандидат в ADR.

## Платформа

- **Kotlin**, Jetpack Compose, Material 3.
- **minSdk 26** (Android 8.0). Обоснование: `AudioTrack.PERFORMANCE_MODE_POWER_SAVING` появился в API 26, и это прямо наш батарейный бюджет. Ниже 26 — меньше 1 % активных устройств.
- **targetSdk** — последний доступный на момент релиза. Android 14+ требует объявлять тип foreground-сервиса (`mediaPlayback`) — учитываем сразу.
- Только Android. iOS — не раньше, чем 1.0 докажет спрос; Compose Multiplatform на аудио-ядро всё равно не распространится, ядро придётся писать отдельно.

## Модульная структура

```
:app                     навигация, DI-граф, точка входа
:core:audio              DSP, генераторы, микшер, рендер-поток   ← ядро продукта
:core:playback           foreground service, MediaSession, audio focus
:core:data               DataStore/Room, пресеты, настройки, статус подписки
:core:designsystem       токены, тема, скины, общие компоненты
:core:i18n               форматирование, плюрализация, утилиты локали
:feature:player          главный экран
:feature:mixer           слои
:feature:presets         библиотека пресетов
:feature:settings        настройки
:feature:paywall         покупки
:billing                 обёртка над Play Billing
```

Правило зависимостей: `feature:*` не знают друг о друге и не зависят от `:app`; `:core:audio` не зависит ни от чего из Android UI и покрыт unit-тестами на JVM.

## Аудио-ядро

**Выбор API.** Не ExoPlayer/Media3 для генерации — он заточен под декодирование потоков, нам нужен свой микшер. Берём **`AudioTrack` в `MODE_STREAM`** с собственным рендер-потоком:

- буфер намеренно большой (100–200 мс) — латентность нам не важна, а редкие пробуждения процессора напрямую экономят батарею;
- `PERFORMANCE_MODE_POWER_SAVING`;
- 44.1 кГц, float PCM, стерео; для чисто низкочастотных пресетов рассматриваем 32 кГц;
- рендер-цикл: заполнить буфер → микшировать слои → лимитер → `write()` (блокирующий вызов сам задаёт темп, никаких таймеров).

Media3 используем только для **сэмплов природных слоёв** и для `MediaSession` (уведомление, lock screen, Bluetooth, кнопки гарнитуры).

**Запасной вариант:** если замеры этапа 1 не сойдутся — переносим микшер на C++ через **Oboe/AAudio**. Интерфейс ядра проектируем так, чтобы замена реализации не задела остальной код.

**Генераторы.** Каждый — реализация одного интерфейса `NoiseSource { fun render(out: FloatArray, frames: Int) }`, stateless снаружи, с собственным RNG (xorshift128+, не `java.util.Random` — он синхронизирован и аллоцирует).

Цепочка обработки слоя: `generator → tilt-фильтр → modulation (LFO) → room (LPF + reverb) → gain/pan → в общий микс → master limiter`.

**Стерео-декорреляция** обязательна: два независимых потока шума или один поток с декоррелирующим all-pass на втором канале. Моно-шум в наушниках воспринимается «внутри головы» и утомляет за часы — это то, на чём валятся дешёвые конкуренты.

**Тестируемость DSP.** Unit-тесты на JVM: рендерим N секунд, гоняем FFT, проверяем наклон спектра, отсутствие DC-смещения, отсутствие клиппинга, детерминированность при фиксированном seed. Это наша страховка от регрессий в самом ценном модуле.

## Воспроизведение и жизненный цикл

- Foreground service типа `mediaPlayback`, стартует вместе со звуком, живёт всю ночь.
- Уведомление с play/pause, таймером и текущим пресетом.
- Audio focus: при звонке — пауза, при уведомлении другого приложения — duck, после — плавное восстановление.
- Wake lock не берём — foreground-сервиса с активным `AudioTrack` достаточно; проверяем поведение под Doze и у агрессивных вендоров (Xiaomi, Huawei, Samsung) отдельным чек-листом устройств.
- Восстановление состояния после kill'а системой.

## Данные

- **Proto DataStore** для настроек и пресетов — типобезопасно, асинхронно, без SQL там, где его не нужно.
- **Room** — только если появится большая библиотека скачанных сэмплов с метаданными.
- Статус подписки кешируется локально с разумным TTL: приложение обязано работать офлайн неделями.

## DI и асинхронность

Hilt; корутины и `Flow` для UI-состояния; аудио-поток — обычный `Thread` с повышенным приоритетом, не корутина (нельзя отдавать рендер на откуп диспетчеру).

## Монетизация

Google Play Billing напрямую или **RevenueCat**. RevenueCat экономит 1–2 недели и даёт готовую аналитику подписок, но берёт комиссию и добавляет сетевую зависимость в место, где мы обещали офлайн. **[?]** — решаем в этапе 0. Моё предложение: свой тонкий слой на Play Billing, потому что у нас всего 3 SKU и офлайн-приоритет.

## Качество и CI

- ktlint + detekt, обязательны в PR.
- Unit-тесты: ядро DSP, вьюмодели, биллинг-логика.
- Скриншот-тесты (Roborazzi) на ключевые экраны × темы × локали.
- Instrumented-тесты на основные сценарии.
- Macrobenchmark: холодный старт, время до звука, энергопрофиль.
- GitHub Actions: сборка + проверки на каждый PR, публикация в internal track через Gradle Play Publisher по тегу.
- R8/ProGuard, App Bundle, отслеживание размера APK (порог — блокер, если превысили).

## Приватность

- Аналитика только opt-in, без идентификаторов устройства и без содержимого пресетов.
- Никаких трекеров в свободной версии.
- Play Data Safety заполняется честно — расхождение с реальностью стоит снятия с публикации.
